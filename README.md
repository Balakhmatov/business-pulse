# Бизнес Пульс

Прототип панели собственника офлайн-бизнеса с точными расчётами и интерпретацией OpenAI.

## Архитектура

- **Демо:** GitHub Pages, три синтетические компании (клиника, магазин, кофейня). CSV и Excel (.xlsx) импортируются только в браузере; демоданные не передаются на сервер.
- **Моя компания:** Telegram Mini App подтверждает вход подписанными `initData`; серверный API `api/server.mjs` работает на VPS через `https://pulse.cityai.site/api/`. Отчёты сохраняются в отдельную SQLite базу. Новые CSV и Excel-файлы (.xlsx) пополняют историю, совпадающие операции обновляются по стабильному ID и идентичности строки. Ранее сохранённые операции не удаляются; повторная загрузка без изменений не вызывает OpenAI.
- **Аналитика:** Node.js считает выручку, средний чек, количество чеков, изменения и динамику без ИИ.
- **Интерпретация:** `api/ai.mjs` отправляет OpenAI только агрегаты без строк CSV, Telegram ID, имён товаров/услуг, файлов и покупателей. Модель `gpt-6-luna` возвращает структурированные выводы. Результат хранится в SQLite до следующего импорта.
- **Fallback:** при отсутствии ключа, ошибке или ожидании OpenAI остаются доступными расчёты и выводы по правилам.
- **Bot:** `bot/index.mjs` — отдельный systemd-процесс с персональной утренней сводкой и кэшированными аналитическими выводами OpenAI, без повторных запросов к модели.

## Серверный OpenAI

API должен получать два независимых файла с секретами: существующий `/etc/business-pulse/bot.env` для Telegram и новый `/etc/business-pulse/openai.env` для OpenAI. Ни один из них нельзя коммитить.

Создать `openai.env` с правами `600` (на сервере):

```ini
BP_OPENAI_API_KEY=your_key_here
BP_OPENAI_MODEL=gpt-6-luna
```

Сервис `deploy/business-pulse-api.service` читает оба EnvironmentFile. После изменения unit:

```bash
sudo install -m 644 deploy/business-pulse-api.service /etc/systemd/system/business-pulse-api.service
sudo systemctl daemon-reload
sudo systemctl restart business-pulse-api
sudo systemctl status business-pulse-api --no-pager
```

Проверки (без авторизации должен вернуться 401 для личных маршрутов):

```bash
curl -i https://pulse.cityai.site/api/health
curl -i https://pulse.cityai.site/api/analysis
```

Анализ автоматически стартует после успешной загрузки CSV или XLSX. Для ранее загруженного отчёта начнётся при первом открытии личного раздела после настройки ключа. Ошибки OpenAI логируются без ключей и исходных данных. При ошибке сохраняются показатели и fallback; последующие попытки ограничены интервалом 10 минут.

## Понятные названия показателей для владельца

В интерфейсе, при импорте и в утренней сводке вместо бухгалтерской «выручки» используем **«Продажи»** — стоимость уже оказанных услуг и переданных товаров, в том числе ещё не оплаченных. **«Поступления»** — деньги, фактически полученные компанией, включая авансы. **«Суммы без уточнения»** — старые выгрузки, для которых пока неизвестно, что означают суммы. Эти три показателя никогда не суммируются между собой. Технические значения API/SQLite `cash_receipts`, `recognized_revenue`, `unverified` остаются прежними, как и математические расчёты. Дни без строк не должны подаваться как подтверждённые дни без продаж.

## Раздельный финансовый учёт (MVP)

- Каждый импорт личной компании получает **подтверждённый пользователем финансовый тип**: `cash_receipts` — реально полученные платежи, включая авансы; `recognized_revenue` — стоимость выполненных продаж / оказанных услуг; `unverified` — тип суммы не подтверждён. Для категории выполненной выручки интерфейс дополнительно требует подтверждения, что авансы без исполнения и неоплаченные счета не включены.
- Миграция `operations.financial_basis` присваивает **всем старым операциям `unverified`**, сохраняя исходные ID, суммы, даты, SHA идентичности, историю импорта и возможность отката старых исправлений. Старую выгрузку запрещено переименовывать в проверенную выручку или поступления без пересмотра источника и явного повторного импорта.
- Новые `cash_receipts` и `recognized_revenue` получают независимые пространства идентичности операций: один ID чека может встречаться в обоих учётах, но сумма одного типа не перезаписывает другой. Новые корректировки и отмены тоже изолированы по выбранному типу. История загрузок показывает тип; отмена партии восстанавливает только её изменения.
- Панель владельца показывает **три независимые суммы**: поступления, выполненная выручка, старые данные без подтверждённого типа. По нажатию график, средняя операция, динамика и топ позиций переключаются на выбранный показатель. В Telegram-дайджесте типы разделены. Выводы AI строятся по одному выбранному сервером показателю; устаревший объединённый AI-кэш один раз инвалидируется при обновлении схемы.
- Поступления **не равны** признанной выручке: аванс увеличивает только книгу поступлений; исполнение обязательства учитывается как выручка только при явной отдельной выгрузке выполненных операций. Система **не** превращает поступление в выручку автоматически, не рассчитывает остатки неотработанных авансов и не проводит бухгалтерскую сверку взаиморасчётов.
- Для новых данных `unverified` по-прежнему допустим только отдельный неклассифицированный показатель. Название заголовка `Сумма` само по себе не подтверждает тип; форматы наподобие `Факт поступления денег` подсказывают полученную оплату, но пользователь может изменить классификацию.

## Ограничения прототипа

- Импорт CSV (UTF-8, Windows-1251) и Excel (.xlsx). При нескольких листах пользователь выбирает лист. Заголовки и соответствие столбцов проверяются перед загрузкой. Файлы до 16 МБ; в «Мою компанию» — до 10 000 операций за одну загрузку и около 6 МБ JSON.
- Старые двоичные Excel .xls пока не поддерживаются: сохраните их как .xlsx. В Excel текстовые ID чеков с ведущими нулями сохраняйте именно в текстовом формате; даты должны быть распознаны как даты.
- XLSX читается локально браузерной библиотекой read-excel-file 6.0.0. Если конкретная выгрузка содержит несовместимые пустые XML-ячейки или обрезанные строки, автоматически включается резервный ExcelJS 4.4.0 (ленивая загрузка с CDN). Для экономии трафика резервный парсер не загружается на обычных файлах. Исходный Excel-файл на API не передаётся; в личном разделе сервер получает только нормализованные операции для хранения в SQLite. Для первой загрузки библиотек требуется доступ к CDN.
- **Универсальный импорт (первый этап):** `smart-import.js` ищет строку заголовков в первых 60 строках (включая шапки отчётов), оценивает названия **и содержимое** столбцов, подбирает дату, ID чека/визита, номенклатуру, сумму и статус среди большого количества дополнительных полей. Пользователь видит соответствия, примеры операций и ошибки и подтверждает импорт. Повторяющиеся заголовки и итоговые строки отбрасываются. Сводные отчёты и суммы по периодам не импортируются как отдельные операции. При нескольких похожих денежных столбцах выбор суммы остаётся за пользователем. Если неизвестный заголовок не распознан, можно настроить вручную.
- **ИИ и память форматов:** после локального распознавания клиент запрашивает сохранённый шаблон компании по хэшу нормализованных заголовков. Если подходящий шаблон отсутствует и есть неоднозначность, защищённый API может запросить у OpenAI подсказку: передаются только названия столбцов (с маскированием email/телефонов/длинных чисел) и агрегированные доли типов значений; **не передаются** исходные строки, идентификаторы чеков, реальные суммы, файл или Telegram-идентификатор. Лимит — не более одного вызова ИИ в 10 минут на компанию. Модель рекомендует индексы столбцов и отдельно возвращает вид денежного показателя (фактическое поступление, отражённая выручка, начисление, аванс, долг, смешанный или неизвестный), уверенность и признаки возможных рисков (предоплаты, рассрочки, возвраты, НДС, дебиторка, двойной учёт). Результат проверяется валидатором и человеком, а не принимается за бухгалтерский факт. После успешного импорта сервер сохраняет подтверждённый шаблон (до 30 форматов на компанию, только структурные хэши и индексы). Повторное использование подтверждённого шаблона не вызывает ИИ. **Неподтверждённые предложения распознавания** отдельно сохраняются по компании и сигнатуре заголовков на 7 дней, чтобы при повторном открытии файла или перезапуске API не терять ранее найденные поля и не повторять платный запрос. Черновая подсказка не считается подтверждённым шаблоном; успешный импорт переносит подтверждённые соответствия в постоянные шаблоны и удаляет черновик. При сбое сервиса предусмотрена одна ручная повторная попытка (не больше двух обращений к модели в 10 минут на компанию); ручной импорт всегда остаётся доступен. Падение OpenAI не останавливает обычный импорт. У разных компаний шаблоны изолированы; при изменении состава/порядка столбцов требуется новое подтверждение. Сам `/api/import` и накопительная дедупликация неизменны.

- **Финансовый контроль до импорта:** независимо от OpenAI браузер проверяет названия выбранных полей и блокирует явные начисления, авансы, долги, НДС, цену единицы и количество как денежную сумму операции. Явное подтверждение требуется только при существенных признаках риска: авансы и предоплаты, частичные платежи, смешанные денежные показатели, дебиторская задолженность либо возможный двойной учёт. Обычные оплаченные операции импортируются без дополнительного чекбокса. Общие замечания о НДС, возвратах или невысокой уверенности модели остаются информационными и сами по себе не блокируют импорт. Неуверенность ИИ сама по себе не запрещает ручную загрузку валидных операций, но отображается пользователю. **Это не полноценная бухгалтерская сверка:** реальное назначение операций, зачёт авансов, признание выручки, взаиморасчёты и распределение частичных платежей по одним названиям столбцов определить невозможно. Для этого понадобится дальнейший анализ строк и отдельная модель учёта. Указанные проверки не вычисляют прибыль или рентабельность.
- AI-консультант с диалогом **не реализован** — только автоматические краткие выводы.
- Не загружать персональные данные пациентов, клиентов и другую конфиденциальную информацию: необходимо отдельно проработать требования безопасности, приватности и правовые основания.
- Выводы ИИ — интерпретация агрегированной статистики, а не доказанные причины или замена финансовому аудиту.

## Автоматическое развёртывание и накопительная история

В VPS включается отдельный **systemd-таймер каждые 15 секунд**: он проверяет SHA ветки `main` через `git ls-remote`, и при изменениях запускает `deploy/release.sh` с тестами, резервной копией SQLite, перезапуском двух отдельных служб и откатом при ошибке. **GitHub Actions и GitHub SSH-секреты не используются.** Первичная настройка — `bash deploy/install-poller.sh` после `git pull`. CityAI не затрагивается. Подробнее: [deploy/README.md](deploy/README.md).

**Контроль качества импорта и история (MVP):**
- Клиент проверяет все распознанные строки до передачи на сервер. Неверная дата, сумма, пустой ID или двусмысленный десятичный разделитель блокируют загрузку целиком; пользователь видит номера проблемных строк.
- Оплаченные и возвращённые операции учитываются отдельно, явно неоплаченные пропускаются. Если файл содержит отмены, импорт **блокируется** до отдельной сверки с ранее сохранёнными операциями: пропуск отмены мог бы завысить цифры. Это намеренное ограничение безопасности.
- Каждая успешная загрузка фиксируется в `import_batches`, изменения сумм — в `import_batch_changes`. `GET /api/import/history` показывает историю только своей компании; `POST /api/import/undo` (с `batch_id`) атомарно отменяет только последнюю действующую загрузку. Возвращаются прежние значения и метаданные; отчёт и AI-кэш пересчитываются. При конфликте отмена отклоняется без частичных изменений. Для экономии диска хранятся последние 100 метаданных загрузок и журналы изменений последних 5 действующих загрузок.
- Новые API защищены проверкой Telegram `initData` и привязкой к компании. `reset-test-data` удаляет и историю тестовых партий, чтобы их нельзя было восстановить отменой после очистки.

**Точечная сверка исправлений и отмен (MVP, опционально):**
- В окне импорта у личной компании можно включить «Исправить или отменить ранее загруженные операции». Обычный импорт и накопление истории остаются режимом по умолчанию.
- Режим сверяет **только идентификаторы операций, которые действительно перечислены в загруженном файле**. Отсутствие старых операций в частичной выгрузке **никогда не удаляет** их из базы. Перенос даты, изменение суммы, услуги или статуса с тем же уникальным ID исправляет одну запись; явный статус отмены удаляет только найденную операцию с тем же ID. Возврат отдельным платежом продолжает учитываться как отдельная отрицательная операция.
- Если один ID уже встречается в базе для нескольких позиций, он повторяется в исправляющем файле или отмена ссылается на неизвестный ID, сверка отклоняется. Нужна детализация с уникальным ID строки, а не общим номером чека. Максимум 1000 операций за одну сверку.
- Сначала вызывается `POST /api/import/corrections/preview`. API показывает число новых/изменённых/отменённых операций, переносы дат и старые/новые суммы. Пользователь отдельно подтверждает список. `POST /api/import/corrections/apply` использует краткоживущую (10 минут) подписанную проверку, повторно сверяет актуальное состояние БД под блокировкой SQLite и атомарно фиксирует либо отклоняет весь пакет.
- Журнал `operation_correction_changes` хранит предыдущие и новые состояния изменённых операций; через историю загрузок отмена последнего исправления восстанавливает даты, суммы, статусы и удалённые операции без воздействия на другие компании. После изменений аналитика пересчитывается. Обработку выполняет тот же проверенный Telegram `initData`.
- Сверка **не считает неполную или выборочную выгрузку полной**, не удаляет «пропавшие» операции и не делает бухгалтерских выводов по авансам или признанию выручки. Полная синхронизация реестра по периоду и построчным ID — отдельный этап.

**Оставшиеся ограничения перед платным пилотом:** изменение даты, смена идентификатора, удаление строки в старой выгрузке, сторнирование уже сохранённой продажи требуют явной модели сверки (надёжного идентификатора строки и периода источника); смешение начислений с денежными поступлениями ещё не допускается считать полноценной бухгалтерской аналитикой. Нужны испытания на обезличенных реальных выгрузках, процедура восстановления резервной копии и мониторинг задач/рассылки. Файлы импорта до 10 000 строк; анализ OpenAI повторяется только после фактических изменений в операциях.
